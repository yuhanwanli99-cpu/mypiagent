## 二、漏检的四个推理跳跃（我跳过了什么）

### 跳跃 1：把症状当成了独立问题

```
我看到：500+ recovery 文件
我说：  "pi-hermes-memory 有磁盘写入死循环"（正确但不完整）
我该问：这个死循环是什么触发的？为什么在 7月14日开始，7月16日达到峰值？
```

**我停在了"命名问题"这一步，没有继续追问"触发机制"。**

### 跳跃 2：没有做时间线交叉分析

```
我看到：live2Dai 有 8 个孤儿 session（7月16日 12:19-15:43）
我看到：hermes recovery 文件在 7月16日 10:09 有 14次/16秒的爆发
我该做：把这两个时间序列放在同一个坐标系里对比
结果：  没做。它们在我的分析中是两个独立的段落。
```

**如果我把时间线对齐，立刻就能看到 causal chain：hermes 雪崩 → Pi 无法启动 → 孤儿 session。**

### 跳跃 3：把"并发写入"当成了理论问题，没当成已发生的事故

```
外部评审说："mailbox 并发写碰撞风险"
我说：    "评审很到位，我来补原子写脚本"
我该说：  "等等，这就是我已经看到的 500 个 recovery 文件的原因！"
```

**我把评审提出的风险当成"未来可能发生的问题"，而它其实已经是"正在发生的灾难"。** 评审人没有看到 recovery 文件，纯靠读文档就推断出了并发写入风险——而我看到了 recovery 文件，却没有回溯到文档中的同一缺陷。

### 跳跃 4：没有读 recovery 文件的内容

```
第一轮：只看到文件名列表（500+ 个），没点进去读
第二轮：读了内容才发现是用户积累的经验教训，不是空文件
```

**如果第一轮就读一个 recovery 文件，我会立刻明白这不是无意义的垃圾文件，而是有价值数据的反复抢救失败——这本身就是一个更强的告警信号。**

## 三、为什么会跳过去（认知层面的原因）

### 3.1 探索顺序的 bias

第一轮的探索路径：

```
1. 看项目结构 → piagent/.pi/ 下的 SPOQ 配置
2. 看全局配置 → settings.json, models.json, agents
3. 看 sessions → 注意到孤儿 session
4. 看 pi-hermes-memory → 500+ 文件，"这是崩溃证据"
5. 然后跳到写 migration guide
```

问题在 **步骤 4→5 的跳跃**：我在收集到了足够异常的信号后，没有进入"调查模式"，而是进入了"记录/归档模式"。"500+ 个文件"被当成"注意事项"放进文档的 §5.2，而不是被当成"必须立即解释的核心谜题"。

### 3.2 "迁移"框架的锚定效应

用户的需求是"写一份迁移指南"。这个框架让我把注意力放在了"如何正确配置"上，而不是"现有配置为什么崩溃了"。recovery 文件被当成了"迁移时不要拷贝的脏数据"，而不是"揭示架构缺陷的法医证据"。

### 3.3 外部评审的"确认偏误"

当用户把外部评审发来时，评审中提到了并发写入风险。我当时的反应是"评审很到位，我来补脚本"——这是**确认偏误**：评审说出了我隐约知道但没明确表达的问题，我就把它当成了"新发现"来处理，而不是回头检查已有的证据。

## 四、如果重来，正确流程是什么

```

  ├── 孤儿 session（meta 无 jsonl）← 异常
  ├── API Key 硬编码              ← 异常

Step 2: 时间线重建（没做）
  ├── 提取所有 recovery 文件的时间戳
  ├── 提取所有孤儿 session 的时间戳
  ├── 对齐到同一时间轴

Step 3: 因果链重建（没做）
  ├── 寻找触发事件（7月16日 09:06 live2Dai session 派发了 Explore agent）
  ├── 追踪事件后果（09:47 hermes 开始故障，10:09 雪崩）

Step 4: 读取内容验证（第二轮才做）
  ├── 打开一个 recovery 文件
  ├── 确认不是空文件（50+ 条经验教训）
  └── 确认损坏的是用户数据，不是临时文件

Step 5: 输出根因报告（没做，现在才做）
```

## 五、改进措施

### 5.1 加入 AGENTS.md / lessons-learned

```markdown
[insight] Phase 0 探索发现多个独立异常信号（大量 recovery 文件 + 孤儿 session + 硬编码 Key）
时，必须先做时间线交叉分析再下结论。单一信号可能是偶然，信号群的时空聚集几乎一定是系统缺陷。
判断标准：同一时段内 ≥ 2 类异常同时出现 → 立即进入"关联分析"而非"分类归档"。
```

### 5.2 在 pi-validate.sh 中加入因果链检测

当前脚本只检测 recovery 文件数量。应增加：

```bash
# 新增：检测最近的孤儿 session 时间是否与 hermes 雪崩时间重叠
# 如果重叠 → 报告 "CONCURRENT WRITE CASCADE DETECTED"
```

### 5.3 修订 migration guide 的 §5.2

原文只说了"不要拷贝旧 hermes 目录"，应该补充：

> **根因**：SPOQ 多 agent 并发写入 `.failures.md` 无原子写保护，导致文件损坏 →
> recovery 机制自身也并发触发 → 死循环 → Pi 启动阻塞。在新机器上，配合
> `atomic-write.sh` 虽不能直接修复 hermes 内部写入，但可以通过启动前检查避免带病运行。

## 六、结论

**P0 风险没有被第一轮发现，不是因为信息不够，而是因为我没有把已经收集到的四个独立信号串联起来做时间线交叉分析。**

四个信号各自都是明显的 P0 告警，但我的处理方式是把它们当成独立问题归档到文档的不同章节，而不是在发现时立即停下手里的"写文档"工作，切换到"事件调查"模式。

这个教训本身已经记录到本次的经验反馈中——未来任何 Phase 0 探索，一旦发现 ≥ 2 类异常信号在时间上重叠，必须先做因果链重建再继续。
