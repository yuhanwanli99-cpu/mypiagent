# SPOQ SOP — 状态机驱动的 agents 集群标准作业流程

> 定位：本项目是一个普通 agent 集群节点，与 Claude Code / Hermes 等 CLI 同项目并存。
> 本 SOP 定义主代理（指挥官）如何把用户请求拆成固定角色流水线执行。
> 状态机是主代理单次任务内的"我正在哪一步"记忆假体，**不做项目级任务台账，不持久化到项目文件**（持久化靠 pi 自身 session 能力）。

---

## 0. 铁律

1. **不信任单 agent 处理多件事**——任何角色只做一件事，交接物是唯一通信手段。
2. **决策权不交给弱模型**——pro/flash 都只填 schema、提选项、执行；拍板权在：确定性规则 + 人工 Gate。
3. **判断权结构排除**——能在 schema 里排除的决策字段就不存在（如研究员的 decision 字段），不靠"提醒模型别做"。
4. **任务完成即清空**——DAG 全 done 或用户终止，状态机立即归零，不留痕迹给下一个请求。

## 2. 模型/参数配置表

> **DeepSeek 官方规则（api-docs.deepseek.com/guides/thinking_mode）**：思考模式开启时 `temperature`/`top_p` 全部不生效。控制参数是 `thinking` 开关 + `reasoning_effort`（low/high/max）。
> **官方基准（DeepSeek-V4-Flash-0731 README）**：`Flash-Max achieves comparable reasoning performance to the Pro version`——Flash 开 max 思考 ≈ Pro，但便宜 3-6 倍。**pro 只留给最复杂的决策**。
> 思考模式三档（官方）：Non-think=快/直觉/日常；Think High=有意识分析/复杂求解/规划；Think Max=探索推理能力边界（token 消耗最大）。

| 角色 | 模型 | thinking | temp/top_p | 理由 |
|---|---|---|---|---|
| Router | flash（3票） | off | 0.0 / 1.0 | 纯分类，3票取多数，greedy（API 调用直接设，非子代理） |
| 需求分析师 | flash | max | （思考模式无效，不设） | Flash-Max 推理 ≈ Pro；L1 推理活，开 max 保准 |
| 检索员 | flash | off | 0.2 / 0.9 | 取数+结构化摘要，关思考省成本，temp 防幻觉 |
| 架构师 | **pro** | max | （无效，不设） | 最复杂决策，Pro 最后防线；选型由人工确认 |
| 方案研究员 | flash | off | 0.2 / 0.9 | 查资料填对比表，关思考省成本 |
| 接口设计师 | flash | max | （无效，不设） | 转换型+Flash-Max 够用，省 3 倍钱 |
| 前端/后端 | flash | off | 0.2 / 0.9 | 照contract抄；关思考快+便宜，temp 0.2 防幻觉 |
| 测试设计师 | flash | off | 0.3 / 0.9 | 用例生成需多样性（temp 0.3），关思考 |
| 测试执行 | — | — | — | 纯函数，无LLM |
| 抽审 | **pro** | max | （无效，不设） | 长程一致性核对，复杂推理，Pro |
| 主代理 | flash | off | 0.2 / 0.9 | 只做流程/格式判断，关思考省成本 |

模型分配规律：**pro 只有 4 个**（需求/架构/接口/抽审）——全是不可逆决策点或长程理解；**flash 有 6 个**——全是取数/照抄/填空。

## 3. 开发流程（SOP 流水线）

### 3.0 三级路由（Router 决定深度）

```
用户输入
  ├─ 单字母 A/B/C 或确认词 ──→ 直接放行（菜单回复，主代理消费）
  └─ 任务文本 → Router（flash×3 投票）
       ├─ SIMPLE  → 主代理直接答/修，零流程（深度 0）
       ├─ COMPLEX → 弱化状态机：计划 + 并行 coder（深度 1）
       └─ LARGE   → 完整状态机（深度 N，见 3.3）
```

### 3.1 SIMPLE（单文件小改动）

```
主代理直接实现 → 完成（不派子代理）
```

### 3.2 COMPLEX（多模块，范围清晰）

```
主代理摸清现状（快速侦察）
  → 生成简短实现计划（分 N 个模块）
  → 同一轮并行派多个 coder（developer）各自实现一块
  → 每个 coder 返回完成摘要 → 主代理汇总 → 交付
（不走需求/架构/测试重角色）
```

### 3.3 LARGE（深度重构/跨平台/长程依赖）——完整状态机

#### 阶段 0：任务分解

```
① 主代理派多个侦察员（flash，并行）——按模块分片摸项目现状
   侦察范围粗分：Android 端 / PC 端 / 共享层 / 需求目标相关
   每个侦察员产出分片现状报告 → .pi/spoq/recon-{模块}.md
   （禁止一个侦察员扛全项目）
② 主代理汇合 → 任务分解清单：
   模块 ID | 名称 | 现状摘要(1行) | 改动性质(重构/新增/修) | 涉及文件(预估) | 依赖模块 | 优先级 | 规模档(SIMPLE/COMPLEX/LARGE)
③ 依赖分组（主代理机械算，随清单一起展示给用户）：
   同批次内并行、批次间串行；批次边界 = 天然检查点
   （批次 1 全部 GREEN 后可先做批次内集成验证再放行批次 2）
④ 停下向用户确认分解方案（人工介入①）：删/合并/改优先级/指定先做哪批
```

#### 阶段 1：接口契约（按模块/批次拆，不是一份大文件）

```
需求设计师（pro）→ contract-{module}.md（接口签名+数据 schema）
  → 落盘 .pi/spoq/contract-{module}.md（唯一共享真相源）
  → 停下向用户确认契约（人工介入②，可选/按规模）
```

#### 阶段 2：排班（测试经理，pro）

```
测试经理按文件/接口边界配对：每个文件 = tester + coder
  ├─ 文件 X → 子测试员 A' + coder A
  ├─ 文件 Y → 子测试员 B' + coder B
  └─ 文件 Z → 子测试员 C' + coder C
一次排完，各对独立可并行
【文件锁】双向隔离：
  - coder 禁止读 .pi/spoq/tests/（防抄答案）
  - tester 禁止读 .pi/spoq/src/（防对答案出题）
【信息归属】
  - 文件评估（每文件多复杂/接口面）→ 留在测试经理，不进主代理上下文
  - 依赖分组摘要 → 上报主代理（紧凑版：模块+依赖+批次，用于调度+阶段4错误影响面判断）
```

#### 阶段 3：并行 TDD（多文件对同时推进，tester 先做）

```
每对内部循环（互不阻塞）：
  ① tester 依据 contract-{module}.md 写测试（RED）
  ② coder 实现让测试变绿（GREEN）
  ③ 下个行为点 → tester 加测试 → coder 实现 → 循环
【依赖支撑】未完成的依赖模块 → 用契约测试/stub（按契约签名生成），不阻塞并行
【失败转发】测试经理脱敏转发给 coder（只报"期望X实际Y"，不报测试源码）
【熔断】同一行为点 ≥3 次不过 → 上报主代理升级判断（防止无限循环）
【物理隔离】每个 coder 只写自己配对的文件，禁止碰别人的（防 git 冲突）
```

#### 阶段 4：收口（测试经理）

```
全部文件对 GREEN 后，测试经理做合并后整体测试：
  ├─ 通过 → 交付
  └─ 不通过 → 回查原因：
       ① 测试经理定位断点（哪个文件对/哪个接口）
       ② 脱敏上报主代理（现象+【影响面】——该接口被哪些下游引用）
       ▼
       主代理判断【错误级别】：
       ├─ 小错（局部细节：类型不匹配/字段名错/单点 bug）
       │    → 直接指挥对应 coder 修复细节
       │    → 该对 tester 重跑 → GREEN → 回整体测试
       └─ 大错（结构性：契约缺陷/架构假设不成立/跨文件依赖设计错）
            → 中止该模块，回【架构分析 + 环境分析】
            → 修正契约（回需求设计师）/ 架构（回架构师）→ 重新排班
            → 该模块 TDD 重写文件（绝不在错架构上打补丁）→ 整体测试
【测试质量把关】测试经理抽查：测试断言必须来自 contract.md、机械可校验
  （防 tester 写错测试 → coder 对着错测试实现 → 测试绿但代码假）
```

## 4. 路由规则（硬约束，实现时必须写死）

### R1 · 缺口驱动迭代 + 无进展熔断（防死循环，但不硬性限制轮数）
- 调研/查证阶段不是固定 2 轮：**缺口（gap）未闭合就继续派**，每个缺口由独立检索员负责（多 agent 并行，每个只填 1-3 个缺口）。
- **闭合判断**：缺口 filled = 有来源支撑的结论；unfilled = 有 ≥3 检索词 + 明确原因（如"该数据不公开"）。
- **熔断（防死循环）**：某一批检索员全部返回后，若新增闭合缺口数 = 0（无进展）→ 停止派发，剩余缺口全部标 unfilled 进 Gate，由人工决定。
- **单缺口重派**：单个缺口被标 unfilled 但人工/主代理认为值得再试 → 可单独重派一次（不重派整批）。
- 主代理按缺口拆批，禁止把一个 agent 同时派去"合并文件+对账+构建核实"（单一 agent 扛多职 = turn limit 爆 + 上下文失真）。

### R2 · deviationFromSpec 路由
- 实现产出中 `deviationFromSpec` 非空 → **自动路由给需求设计师复核**（不是主代理、不是架构师）。
- 需求设计师判断：偏差可接受 → 记录进 contract 修订；偏差破坏需求 → 升级人工确认。
- 主代理**不做内容判断**，只执行路由。

### R3 · 测试失败路由（LARGE 错误分级）
- 整体测试失败 → 测试经理定位断点 + 脱敏上报主代理（含影响面）。
- 主代理分级：
  - **小错**（局部细节：类型不匹配/字段名错/单点 bug）→ 直接指挥对应 coder 修复 → 该对 tester 重跑 → 回整体测试。
  - **大错**（结构性：契约缺陷/架构假设不成立/跨文件依赖设计错）→ 中止该模块，回架构+环境分析 → 修正契约/架构 → 重新排班 → TDD 重写文件。
- 绝不在错架构上打补丁（那是技术债源头）。

### R4 · 抽审触发（无模糊"低频"）
- **`tier=premium` 的模块自动触发抽审**，绑定架构.md 的 tier 标注，无需额外人工判断"算不算高风险"。
- 非 premium 模块默认不抽审（除非人工主动要求）。

### R5 · TDD 循环熔断
- 同一行为点 ≥3 次 RED 不过 → 上报主代理升级判断（防 tester/coder 无限循环）。

### R6 · 并行写隔离
- 每个 coder 只写自己配对的文件，禁止碰别人的（防 git 冲突）。
- 未完成依赖模块 → 用契约测试/stub（按契约签名生成），不阻塞并行。

## 5. 交接物 schema（每层输出必须严格按此填空，禁止自由发挥）

### 5.0 交接物落盘路径（统一，防止各写各的）
- **所有交接物固定写入 `<项目根目录>/.pi/spoq/` 目录**（项目根 = 主代理派发时给的 CWD）。
- 文件名固定：`recon-{模块}.md`（侦察分片）、`task-breakdown.md`（任务分解清单）、`contract-{module}.md`（模块契约）、`schedule.md`（排班表）、`tests/{文件}.test.*`（测试文件）、`src/{文件}`（实现）、`audit-report.md`（一致性报告）。COMPLEX 用 `requirement.md`/`search-report.md`。
- 检索员/侦察员等调研角色只写自己的分片文件（`recon-{模块}.md` / `search-report-{gapid}.md`），禁止整文件覆盖别人的。合并由主代理负责。
- 禁止子代理创建自己的目录约定（如 `spoq/work/`）——路径由主代理在 prompt 中显式指定，子代理不得自创。

### 5.7 任务分解清单（侦察员/主代理 → 阶段0产物）
```markdown
# 任务分解清单
- taskId / 版本
## 模块清单（数组）
- 模块ID | 名称 | 现状摘要(1行) | 改动性质(重构/新增/修) | 涉及文件(预估) | 依赖模块 | 优先级 | 规模档(SIMPLE/COMPLEX/LARGE)
## 依赖分组（批次）
- 批次1: M1,M2,M3 | 批次2: M4 | ...
## 待用户确认项
- 删/合并/改优先级/指定先做哪批
```

### 5.8 排班表（测试经理 → 阶段2产物）
```markdown
# 排班表
- taskId / 关联契约版本
## 配对（数组）
- 文件 | tester | coder | 所属模块 | 批次
## 依赖分组摘要（上报主代理）
- 模块+依赖+批次（紧凑）
```

### 5.1 需求.md（需求分析师 → 架构师；COMPLEX 模式用）
```markdown
# 需求
- taskId / 版本 / 来源（Router标签）
## 用户故事
（≤5条，每条一句话，flash可填）
## 验收标准
- AC1: ...（可测试，机械可校验）
## 边界
- in: ... / out: ...
## 非目标
- ...
## 数据缺口清单（强制，不允许空）
- GAP1: 需要什么数据 | 用途 | 状态: filled/unfilled | 检索词(≥3) | 原因
## 禁止
- 禁止编造数据；缺口必填，无"无"以外的沉默跳过
```

### 5.2 检索报告.md（检索员 → 需求分析师）
```markdown
# 检索报告
- taskId / 关联需求.md版本 / 检索时间
## findings（数组）
- finding_id: R01 | finding(≤50字) | evidence(≤200字) | source(必填) | confidence: high/medium/low | relevance(需求.md编号)
## gap_status（对需求.md数据缺口的逐条回应，强制）
- gap_id | status: filled/unfilled | filled→finding_id | unfilled→检索词(≥3)+原因
## 禁止
- 禁止粘贴原始网页/长文档（>200字必须摘要）
- 禁止无来源结论（无来源→confidence=low或进gap_status.unfilled）
```

### 5.3 架构.md（架构师 → 接口设计师/测试设计师）
```markdown
# 架构
- taskId / 关联需求.md版本
## 技术选型（选项+取舍，不是结论）
- 方案A/B/C | 各 pros/cons | 取舍理由 | 来源（引用方案对比.md）
## 模块划分
- M1: 职责 | 依赖 | tier: fast/standard/premium   ← tier 用于 R4 抽审触发
## 接口 contract 草案（交接给接口设计师）
- 模块间依赖契约要点
## 禁止
- 禁止直接拍板（选型结论由人工确认）
- 数据不足 → 打回 L1，不猜
```

### 5.4 方案对比.md（方案研究员 → 架构师）
```markdown
# 方案对比
- taskId / 关联需求.md版本 / 关联架构方向
## candidates（数组）
- option_id: S01 | option_name | summary(≤50字) | pros(3-5条,≤30字) | cons(3-5条,≤30字) | adoption_evidence(必填来源) | risk: 高/中/低+一句话 | tier_hint: fast/standard/premium
## comparison（强制，固定维度表）
- 维度: 成本/生态成熟度/学习曲线/与现有代码兼容性/长期维护
- 每维度: 各方案评级(高/中/低) + 一句话依据
## open_questions（强制）
- 需要额外调研才能定论的方案点 → 必须列出
## 决策边界
- 本报告只提供选项和证据
- 【schema 中不存在 decision 字段】← 取舍决策权在架构师 + 人工确认
```

### 5.5 contract.md（接口设计师 → 前后端）
```markdown
# 接口契约（锁定，前后端唯一依据）
- taskId / 版本
## 接口签名
- endpoint/方法 | 入参schema | 出参schema | 错误码
## 数据模型
- 表/对象结构（字段名+类型+必填）
## 修订记录
- v1.0 初始 | deviation 记录（R2 路由后追加）
## 禁止
```

## 6. 主代理执行清单（每轮行为）

1. 首先看收到的 ROUTE 标签，按三种模式执行：
   - `ROUTE=SIMPLE` → 直接实现，不派子代理。
   - `ROUTE=COMPLEX` → 摸清现状 → 生成简短实现计划 → 同一轮并行派多个 coder（developer）各自实现一块，不走完整 SOP。
   - `ROUTE=LARGE` → 走完整状态机：⓪分解→①契约→②排班→③并行TDD→④收口。
2. 用 Agent 工具派发对应角色（`run_in_background=true`）：`Agent(subagent_type, prompt, run_in_background=true)`。subagent_type 见第 1 节角色表。
3. 后台子代理完成 → pi 自动发 `<task-notification>`（含 task-id/status/result 预览）；需要完整结果用 `get_subagent_result`。
4. 收到交接物 → 按 SOP.md 第 5 节 schema 机械校验（字段齐全/来源存在）→ 不通过打回该层重做，通过进下一层。
5. 遇到人工确认点（阶段0分解确认/阶段1契约确认/阶段4错误分级）→ 停下展示给用户，等回复后再继续，禁止自行替用户决策。
6. **上下文瘦身**：收到子代理完成通知后只记录指针（文件路径+一行摘要），绝不把交接物全文读进上下文；需要细节时再读文件。
7. **依赖分组进主代理上下文**（紧凑版：模块+依赖+批次）：用于调度批次放行 + 阶段4错误影响面判断。文件评估细节留在测试经理，不进上下文。
8. LARGE 阶段4：整体测试失败 → 测试经理脱敏上报（含影响面）→ 主代理分级：小错指挥 coder 修细节；大错回架构/环境分析后重排重写。
9. 任务完成 / 用户终止 → 在对话中清空自己的"进行中"认知，不残留。
10. 规模异常（分解后模块数远超 Router 预估）→ 停下向用户展示，问是否降级/分批。

**主代理只做流程/格式判断，不做内容判断。内容判断权在：确定性规则（R1-R6）+ 人工确认点 + schema 结构排除。**

> 注意：状态机不落盘。主代理的"当前在哪一步"完全来自对话上下文记忆（指针式）。pi 会话意外中断 → 靠 pi 自身 session 恢复（`pi --session`）续上，交接物在 .pi/spoq/ 文件里不丢。
