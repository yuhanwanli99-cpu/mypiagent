# SPOQ AGENTS.md — 三级路由 + SOP 角色流水线（v6）

> 本项目（pi agent 集群节点）的编排规则。与 `SOP.md` 配套：本文件是主代理的**顶层执行规则**，`SOP.md` 是**流程细节**。

## 架构总览

```
用户输入
  ├─ 单字母 A/B/C 或确认词 ──→ 直接放行（菜单回复）
  └─ 任务 → Router（flash×3 投票）→ SIMPLE / COMPLEX / LARGE
```

| 级别 | 触发 | 执行 |
|---|---|---|
| **SIMPLE** | 单文件小改动 | 主代理直接答/修，零流程 |
| **COMPLEX** | 多模块但范围清晰 | 主代理生成计划 → 并行派多个 coder |
| **LARGE** | 深度重构/跨平台/长程依赖 | 完整状态机（见 SOP.md 3.3） |

## 铁律

1. **不信任单 agent 处理多件事**——任何角色只做一件事，交接物是唯一通信手段。
2. **决策权不交给弱模型**——pro/flash 都只填 schema、提选项、执行；拍板权在：确定性规则 + 人工确认点。
3. **判断权结构排除**——能在 schema 里排除的决策字段就不存在（如研究员的 decision 字段），不靠"提醒模型别做"。
4. **上下文瘦身**——主代理只记指针（文件路径+摘要），绝不把交接物全文读进上下文。
5. **交接物落盘**——全部写入 `<项目根>/.pi/spoq/`，文件是唯一真相，对话上下文不是。
6. **任务完成即清空**——主代理在对话中清空"进行中"认知，不留痕迹给下一个请求。
7. **测试是 coder 的上级**（LARGE）——tester 先写 RED 测试（TDD），coder 实现 GREEN；文件锁双向隔离防抄答案。
8. **绝不在错架构上打补丁**（LARGE 阶段4）——小错补丁，大错回架构/环境分析后重写。
9. **入口唯一**——用户输入统一走 complexity-gate.ts（Router 分类 + 单字母放行）。
10. **不持久化状态文件**——没有 spoq-state.json、没有 mailbox、没有门禁白名单。调度状态靠主代理上下文记忆（指针式），跨会话靠 pi session + .pi/spoq/ 文件。

## 执行纪律（主代理每轮）

1. 看收到的 `ROUTE=` 标签，按三档执行（见 SOP.md 3.0）。
2. 派子代理用 `Agent(subagent_type, prompt, run_in_background=true)`，subagent_type 见 SOP.md 第 1 节。
3. 子代理完成 → `<task-notification>` 通知；只记指针，不读全文。
4. 收到交接物 → 按 SOP.md 第 5 节 schema 机械校验 → 不合规打回该层。
5. 人工确认点（分解/契约/错误分级）→ 停下等用户，禁止自行决策。
6. LARGE 阶段3 并行 TDD：tester 先写 RED → coder 实现 GREEN，失败信息经测试经理脱敏转发。
7. LARGE 阶段4 收口：整体测试失败 → 测试经理脱敏上报（含影响面）→ 主代理分级（小错补丁/大错重写）。
8. 禁止自己深度探索项目源码——那是子代理的活，主代理只做派发和流程。

## 与外部编排系统的关系

本规则管理 **pi agent 自身内部** 的子代理派发（Router → 侦察/需求/契约/测试/开发角色）。
它不管理 pi 如何被外部系统（Orca/Claude Code/Hermes 等）调用——那是另一层，走各自的通道，互不干扰。
本节点是项目里的普通 agent 集群节点，不抢占"项目任务图谱唯一真相"角色。
